## DevKit workflow adapter

When this skill runs inside a DevKit workflow, generated artifacts are for
audit/handoff. They do not replace the interactive Superpowers brainstorming
conversation.

Follow upstream Superpowers exactly:

1. ask exactly one clarifying question per terminal/chat turn.
2. For text requirements questions, show the question in the terminal/chat and
   wait for the user's answer before asking the next question.
3. During the Q&A, record answered questions, decisions, and accepted
   assumptions in `.vibe/research/<task-id>.md` (working notes — not the gated
   artifact).
4. Do not tell the user to approve the brainstorm step while unresolved
   questions remain, unless the user explicitly accepts them as assumptions.
5. **Output location override (DevKit):** the finalized design spec goes to
   `.vibe/sessions/<segment>/SPEC.md` — the path shown under **Expected
   artifacts** in the current instruction. Do NOT write it to the upstream
   `docs/superpowers/specs/...` default. Upstream allows this: "User
   preferences for spec location override this default."
6. Only after every open question is resolved and the design is locked, write
   `SPEC.md` in full (no placeholders), then ask for approval and transition
   toward `skill.sp.writing-plans`.
7. **Ask via the native ask-question tool, never plain chat text.** Every point
   where upstream says "present the design and get user approval" / "get user
   approval after each section" / "ask the user to review the spec" is a GATE:
   call the editor's ask-question tool (`AskUserQuestion` on opencode/Claude
   Code, `AskQuestion` on Cursor) with options (e.g. Approve / Request changes),
   NOT a plain-text "Does this look right? Should I proceed?" message. Put the
   design/summary as context, keep the question itself a tool call. Only fall
   back to typed input if the tool is genuinely unavailable.
